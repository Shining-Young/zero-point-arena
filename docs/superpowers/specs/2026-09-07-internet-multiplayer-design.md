# 零点行动：互联网联机设计

## 目标

把现有单机人机击杀竞赛升级为可通过互联网游玩的 2–4 人房间游戏。玩家在自己的 Windows 10/11 x64 电脑上运行独立游戏包，通过六位房间码加入同一场比赛。项目不再依赖 Sites；游戏客户端和联机服务器是两个独立产物。

第一版保留现有七号仓库地图、AR-4 步枪、P-12 手枪、三档人机难度、15 次击杀或 5 分钟结束的规则。真人不足时，房主可选择使用人机补足 4 个参赛位置。

## 交付物

1. Windows x64 便携游戏包。玩家解压后双击启动，不要求预装 Node.js，不要求管理员权限。
2. 可部署的 Node.js 联机服务器，包含 Dockerfile、健康检查和环境变量说明。
3. 开发者源码包，保留本地单机模式和原有自动测试。
4. 部署完成后的固定 `wss://` 地址写入发行配置。玩家只接触昵称与房间码，不填写服务器地址。

首个可分发版本不签署 Windows 代码签名证书，因此 Windows 可能显示来源提示。程序不申请管理员权限，也不写入系统目录。

## 玩家流程

启动后进入模式选择：

- 单人训练：沿用当前本地人机模式，可离线运行。
- 创建房间：填写 1–16 个字符的昵称，选择真人上限 2–4、人机补位数量和人机难度。创建成功后显示六位大写字母数字房间码和复制按钮。
- 加入房间：填写昵称和房间码。加入后进入准备大厅。

大厅列出玩家昵称、连接状态、是否准备及机器人位置。创建者是房主；房主可调整机器人数量和难度。所有真人准备后，房主开始比赛。比赛进行中允许使用房间码重连，不允许新玩家占用已锁定的真人位置。

比赛结束后显示比分、击杀、死亡、命中率和爆头数。房主可发起再来一局；玩家也可离开房间返回主菜单。

## 架构

### 客户端

现有 Three.js 渲染、音效、输入和界面继续运行在客户端。战斗引擎拆成三部分：

- `LocalTrainingGame`：保留当前纯本地人机模式。
- `MultiplayerGame`：采集本地输入、发送网络消息、插值显示远端实体并应用服务器事件。
- 共享表现层：地图几何、武器模型、角色模型、HUD、音效和命中反馈。

Windows 游戏壳使用 Electron。它加载打包后的本地前端文件，允许 Pointer Lock，并把联网端点从只读发行配置传给客户端。Electron 主进程不执行游戏规则，不保存密码或令感信息。

### 联机服务器

服务器使用 Node.js、TypeScript 和 `ws`。每个房间在一个进程内维护权威状态：玩家、机器人、比赛时钟、生命值、弹药、重生、比分和最近确认的输入。房间没有玩家后保留 60 秒，然后释放。

服务器无数据库依赖。房间码和重连令牌只存在内存中；服务器重启会结束当前房间。第一版以单实例部署，避免跨实例房间协调。健康检查使用普通 HTTP `/health`，游戏连接使用 `/game` WebSocket 路径。

### 部署

服务器保持平台无关，通过 Docker 部署到支持长连接 WebSocket 的服务。生产环境需要稳定 HTTPS 域名；浏览器和 Electron 客户端使用对应的 `wss://` 地址。部署目标的账号、区域和付费方案在代码完成并验证后确定；项目本身不绑定 Sites 或专有数据库。

## 网络协议

协议使用带版本号的 JSON 消息，首版为 `protocolVersion: 1`。所有消息都有严格的运行时校验，未知类型、超长文本、非法数值和过快发送会被拒绝。

客户端到服务器的主要消息：

- `hello`：协议版本、发行版本和可选重连令牌。
- `create_room`：昵称、真人上限、机器人数量、难度。
- `join_room`：昵称、房间码和可选重连令牌。
- `set_ready`：准备状态。
- `configure_room`：房主修改机器人数量和难度。
- `start_match`：房主开始比赛。
- `input`：递增序号、移动轴、视角、跳跃、蹲伏、冲刺和客户端时间。
- `fire`：武器、射击序号、视角方向和客户端时间。
- `reload`、`switch_weapon`、`leave_room`、`play_again`。

服务器到客户端的主要消息：

- `welcome`：玩家 ID、重连令牌和服务器时间。
- `room_state`：房间码、房主、玩家列表、机器人设置和准备状态。
- `snapshot`：服务器 tick、实体位置、朝向、生命值、当前武器、弹药、比分和比赛时间。
- `combat_event`：射击、命中、爆头、击杀、换弹和重生。
- `match_started`、`match_finished`、`host_changed`、`error`。

每条 WebSocket 消息上限 8 KB。输入消息按玩家限制为每秒 30 条，射击与换弹由武器服务器冷却进一步限制。昵称在服务器端裁剪和转义；不接受客户端提供的 HTML。

## 同步与判定

服务器以每秒 20 tick 更新房间。客户端每秒发送最多 20 份输入状态，并在本地立即预测自己的移动。服务器快照每秒发送 10 次；客户端对其他玩家和机器人使用约 100 毫秒的插值缓冲。

玩家位置由客户端预测、服务器校正。服务器根据最后确认位置、移动速度、碰撞半径和地图障碍拒绝穿墙或瞬移。误差小于 0.35 米时平滑修正，超过该值时拉回服务器位置。

射击完全由服务器结算。服务器检查：玩家存活、未处于换弹状态、射速合法、弹匣有子弹、出生保护已结束、射线与射手朝向相符、目标在射程内，并使用共享障碍数据进行遮挡判断。服务器保留最近 500 毫秒的玩家位置历史，以客户端时间为线索做上限 200 毫秒的延迟补偿；超过范围按当前服务器状态结算。

机器人只在服务器运行。客户端只渲染机器人快照和战斗事件，不能决定机器人命中或死亡。

## 房主、掉线与重连

房主离开时，服务器把房主身份交给加入最早且仍在线的玩家。大厅无人在线时，房间立即关闭；比赛中的房间在最后一人掉线后等待 60 秒。

玩家首次加入会获得随机的 128 位重连令牌，令牌保存在本机应用数据目录。连接中断后，客户端按 1、2、4、8 秒间隔重试。服务器为该玩家保留席位 30 秒；携带正确令牌可恢复原玩家 ID、比分和实体。30 秒后席位转为空位或由机器人补入。

同一令牌建立新连接时，旧连接被关闭，防止一个身份同时控制两个客户端。

## 错误状态

客户端必须显示可操作的中文提示：

- 无法连接：显示重试和返回单人训练。
- 房间不存在或已开始：保留昵称和房间码，允许修改后重试。
- 版本不一致：提示双方更新游戏包，禁止进入比赛。
- 延迟过高：HUD 显示黄色或红色延迟，不自动踢出。
- 服务器重启：明确说明房间已结束，返回主菜单。
- Pointer Lock 被拒绝：保留现有兼容鼠标控制和再次锁定按钮。

## 安全边界

服务器不信任客户端的生命值、分数、弹药、命中结果或机器人状态。房间码不能作为管理权限；房主操作同时校验服务器记录的玩家 ID。重连令牌不写入日志，不通过 URL 查询参数传递。

每个 IP 每分钟最多创建 10 个房间、尝试加入 60 次；单连接每秒最多接收 60 条应用消息。持续违规的连接会被关闭。服务器日志只记录时间、房间生命周期、匿名玩家 ID、错误类型和延迟摘要，不记录昵称或重连令牌。

第一版不承诺抵抗修改客户端或分布式攻击，但服务器判定应阻止常见的改血、改弹药、超射速、瞬移和穿墙命中。

## 测试与验收

共享规则测试继续覆盖地图碰撞、遮挡、寻路、弹药与胜负。新增测试覆盖：

- 创建、加入、准备、开局、满房和房间码冲突。
- 只有房主能修改房间和开始比赛。
- 输入限速、移动速度校验和穿墙回退。
- 射速、弹药、出生保护、遮挡、距离与延迟补偿。
- 机器人由服务器更新并计入同一比分。
- 房主迁移、30 秒重连、重复令牌连接和 60 秒房间释放。
- 协议版本不一致、畸形消息、消息过大和断线。
- 两个真实 WebSocket 客户端完成创建、加入、准备、开局、互相看见、一次击杀、重生和结算。

最终验收要求：

1. 两台不同网络的 Windows 电脑可通过固定服务器地址和房间码加入。
2. 双方可以连续完成一局，位置、射击、击杀、重生和比分一致。
3. 100–180 毫秒模拟延迟和 2% 丢包下，远端移动保持可辨识且不会频繁瞬移。
4. 客户端断网 10 秒后恢复，能在 30 秒保留期内回到原席位。
5. 单人训练仍可离线运行，鼠标锁定和兼容控制保持有效。
6. Windows x64 便携包在未安装 Node.js 的干净环境中启动。
